## 范围与证据

用户报告 1,746 份约 1GB 文件，4 线程严重卡顿，增大线程数未响应且处理后内存不降；状态文字出现类似白块覆盖的裁切。用户授权只读默认本地清单目录。不降低默认 16，不强制垃圾回收，不修改源清单或 CLI 输出。

基线实际读取 1,746 份、1,056,634,317 字节：4 线程 22,869ms，启动同步 349ms，最长 UI 停顿 1,714ms，1,747 次状态更新，托管峰值 1,228,452,136 字节、结束 512,087,000 字节。整批输入失败／冲突，没有有效参考结果。状态区测试复现固定 44px 高、所需 53px 高；这是确定的裁切条件，但没有现场捕获用户所述白块，需实际绘制验收。

## 根因与修复

- 每文件 Progress<int> 队列消息和 ShowResult 每行全表查找：改为工作线程原子更新计数，UI Timer 每 100ms 采样；批量回填一次建行索引。单做此项实测启动降到 19ms、最长停顿降到 250ms，峰值内存仍高，确认两条独立问题。
- 解压 MemoryStream 扩容＋ToArray 和生成完整分块对象：改为受限解压流直接交 protobuf／JSON，格式前缀小范围探测后回放，保留 BOM／空白兼容。文件级 protobuf 投影保留原字段编号，不构造不用的 chunk 对象，完整 schema 不移除。3.22MB／20,000 分块样本分配由 22,563,984 降到 12,088 字节。
- 独立清单快照累积：FileComparer 内增量累加器，每份完成立即合入；失败／冲突立即放弃累计结果，后续只收摘要。并行完成顺序不影响输入来源顺序和第一份输入的路径大小写；发布后禁止继续修改累加器，避免破坏只读快照。
- 状态文字固定行高：Label.AutoSize 配合 AutoSize 行，显式不透明背景。较大字体、窄窗口连续更新进度的裁切回归先红后绿。未以截短或隐藏文字绕过。
- 流式初版将超限且开头损坏输入提前报格式错，原测试捕获；增加固定缓冲 drain，保留原解码上限与压缩错误优先级，不保留 drain 内容。

## 最终实测（同一进程内两轮，不强制 GC）

- 4 线程：4,177／2,907ms；托管峰值 61,671,568／67,309,000；结束 27,778,232／30,701,016；最长停顿 51／45ms；结束私有内存 98,889,728／102,408,192 字节。
- 16 线程：1,787／1,854ms；托管峰值 134,733,904／127,368,408；结束 60,899,200／57,523,896；最长停顿 35／37ms；结束私有内存 116,158,464／123,424,768 字节。
- 两种线程配置均未发布失败整批；不是通过放宽校验或跳过坏文件伪造成功。成功批次仍需存放实际合并清单，不承诺任何输入都只有此内存。
- 中间仅去掉复制／分块对象仍在 16 线程达到约 920MB 峰值，被诊断门槛拒绝，随后改为流式才通过。最终显式门槛为托管峰值低于 256MiB、最长 UI 停顿低于 500ms，未降低线程数或提高门槛绕过。
