# 项目内技能使用约定

## 使用原则

本项目安装 13 个可调用技能和 1 个仅供读取的测试参考目录。技能是给 agent 的工作手册，不是自动运行的保护程序；安装不等于验证通过。

先检查当前运行环境提供的技能列表，再用 `skill` 工具主动加载当前阶段匹配的技能；不是建议用户自己记住后调用。路径由工具返回，附属文件按技能指示读取。一次只加载当前阶段真正需要的技能，不因目录中存在某项技能就启动审查、扫描、重构或安装工具。

## 主动调用检查点

进入下列阶段时，按这里判断是否必须实际加载。已经在本会话加载且仍有完整上下文的技能可复用；压缩后丢失内容则重新加载。不能把“读了本路由表”“准备使用”或输出技能名字算作已调用。

1. **提出方案前**：存在产品歧义时加载 `grilling`；涉及职责、共享逻辑或重要架构设计时加载 `codebase-design`；确实新增/修改业务概念时加载 `domain-modeling`。普通明确的小修不强行跑需求访谈或领域建模。
2. **开始实现前**：C# 工作加载 `csharp-expert`，WinForms 页面工作直接加载更具体的 `winforms-expert`，不为走路由而重复加载前者；新增或修复可测试行为时加载 `tdd`。
3. **开始排错时**：故障和回归加载 `diagnosing-bugs`；定位到相关 .NET 热点后再加载 `analyzing-dotnet-performance`。未复现的问题不直接进入“优化代码”。
4. **测试与安全检查时**：新增/明显修改测试后，用 `assertion-quality` 检查测试的实际断言；重要状态链、安全分支或明确的漏测担忧用 `test-gap-analysis`。涉及文件操作/危险配置的设计用 `sharp-edges`，安全敏感实现的改动审查用 `differential-review`；纯文案不套安全审计。
5. **完整业务改动交付前**：加载 `code-review`，按已确认方案审查实际改动；小型文档调整可以简单自检，不为凑调用数量启动双代理。

用户可以直接看到 `skill` 工具的加载记录，不另行播报、解释或汇总调用了哪些技能。交付聚焦实际效果、验证结果和未验证事项。不要求用户提醒，也不伪造调用记录；用户主动追问时再解释技能选择，用户仍可随时暂停或指定技能。

这些是 agent 的执行规则，不是保证自动触发的程序钩子；不能承诺任何模型都绝不漏调。当前不额外安装自动化插件或 hooks，以免引入第二套流程和宿主维护负担。

## 按阶段路由

| 当前任务 | 使用技能 | 范围 |
| --- | --- | --- |
| 需求存在影响操作、数据安全或验收的歧义 | `grilling` | 先查项目事实，再用具体场景和推荐选项补齐产品决策；小改动不进行冗长访谈 |
| 新增或修正业务术语、记录难以逆转的取舍 | `domain-modeling` | 复用 `GLOSSARY.md` 与 `docs/adr/`，只记录已决定的内容 |
| 设计模块职责、共享逻辑或测试入口 | `codebase-design` | agent 提出推荐方案，重要取舍由用户确认；保持现有分层，不附带全仓重构 |
| 新增行为或修复可测试缺陷 | `tdd` | 对重要行为先观察失败，再实现最小修复；使用既有 xUnit v3 与测试入口 |
| C# 语言、类型、异步、资源生命周期问题 | `csharp-expert` | 专项技能优先，其余使用 C# fallback；第三方 API 仍按规则查询 Context7 |
| 原生桌面界面、布局、控件或交互 | `winforms-expert` | 当前项目为 Windows Forms；保留代码构建控件与共用语言资源方式 |
| 故障、卡顿、异常或行为回归 | `diagnosing-bugs` | 复现原症状、建立反馈、定位根因、修复并验证旧场景 |
| 已定位热点的 .NET 分配、I/O、异步等性能问题 | `analyzing-dotnet-performance` | 只分析相关路径；优化效果另用同条件前后测量证明 |
| 担心现有测试漏掉错误行为 | `test-gap-analysis` | 先映射行为到测试；没有运行验证就不声称缺口已被实验证实 |
| 新增或既有测试是否只“看似验证” | `assertion-quality` | 检查独立期望值、失败、状态和副作用；不追求机械的断言数量指标 |
| 一个完整业务改动交付或提交前 | `code-review` | 分开检查代码规范与需求符合度；包含相关未提交及新文件，小文档改动自检即可 |
| 文件操作或配置接口的安全设计 | `sharp-edges` | 关注根目录约束、链接、覆盖、输入校验、失败与取消保护 |
| 改动路径、解析、网络来源校验或真实移动等安全敏感逻辑 | `differential-review` | 相对基线检查安全回归，并验证具体问题是否可达；不对每个文案改动做安全审计 |

测试分析时直接读取 `.opencode/skills/test-analysis-extensions/SKILL.md` 及其 `extensions/dotnet.md`；该目录是参考资料，不作为技能调用。

## 本项目适配约束

- **用户保留控制权，agent 承担技术分析。** 用效果、操作、风险和维护代价解释推荐方案，让用户能够选择。新功能、交互调整与重要架构变化须先确认方案；涉及数据格式兼容、框架/依赖、不可逆结构、性能与资源明显取舍时，把后果和推荐项交给用户决定。日常类名、测试接口等实现细节在已授权方案内自行处理，但用户随时可追问、否决或要求调整。
- **现有规则不因技能失效。** 技能不授予额外的删除、覆盖、联网、安装、推送或文件访问权限。项目外文件操作、敏感内容和安全删除仍遵守上层规则。发现新的实质冲突时说明并暂停，不擅自选一方。
- **保持项目现状。** 不为了符合示例迁移框架、增加依赖、引入 Designer/MVVM 或替换语言资源与配置结构。`csharp-expert` 是技术路由加语言后备，不代表已安装微软全套插件。
- **使用当前宿主能力。** Bash、Claude 插件命令、Task 工具名和命名专用代理只是上游示例；转换为本环境已有的 PowerShell、文件工具与允许的代理调用。技能里的后台代理按通知收取结果，不轮询。未安装技能或代理不假装调用；能安全验证则继续，缺少关键能力则明确限制。
- **范围与成本受控。** 默认自行完成技术调查；大改动的双轴代码审查可以按 `code-review` 使用两个只读代理。架构多方案并行仅在用户要求比较时使用。不得因技能里出现可选代理就启动大规模 workflow。
- **真实证据优先。** 编译、测试、离屏布局、真实桌面交互和 Designer 验证分别说明，不能相互冒充。性能分析的模式匹配不是性能改善证据。怀疑的安全问题先追踪完整调用与校验，再用隔离样本证明；未证明标注待确认。
- **复用测试与临时目录。** 先读 `docs/testing.md`。程序测试只用既有 runner；新的测试临时文件遵循 `TestTemporaryFiles.Root`，人工日志和截图使用获准的系统临时目录。不在真实游戏目录里做破坏性复现，不为证明测试缺口修改未知用户工作。
- **适度记录与审查。** 需求和任务仍用 `docs/agents/issue-tracker.md` 的本地 Markdown 约定；当前对话的已确认要求也可作为审查依据，不为使用技能强造 spec。按模块交付，验收后按既有 session 编号规则提交；不自动推送。

- 本地变更日期为 2026-11-20。13 个可调用技能的 `SKILL.md` 均增加项目适配说明；另调整了需求提问、技术分工、未提交审查、Windows 排错和不可用代理的相关段落。参考资料保持固定版本的上游内容；必要的失效链接修正单独列在下文。

- 更新时先对照来源清单检查上游差异、许可、引用文件和工具要求，再保留上述适配并更新版本记录；不要直接用全量安装覆盖本地修改。不自动更新，不执行上游附带脚本。
