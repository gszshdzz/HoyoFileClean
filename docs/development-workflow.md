# 不看代码也能指导开发

你保留“做什么、采用什么方案、重要取舍、是否验收通过”的控制权；AI 负责调查、提出建议、在你确认的范围内实现并验证。不懂代码不等于全权委托，也不意味着只能最后看效果。技能由 AI 按阶段主动调用，你不需要记住名字。

## 已安装技能分类

| 类别 | 技能 | 对你有什么用 |
| --- | --- | --- |
| 需求 | `grilling` | 先补齐容易理解错的操作与边界，避免做完才发现不是你要的 |
| 业务术语 | `domain-modeling` | 保持“清单外、缺失、未扫描、受保护”等概念一致，不把清单外文件直接当垃圾 |
| 架构 | `codebase-design` | AI 提出功能划分与共享方案，用通俗后果说明重要取舍，由你确认 |
| 实现 | `csharp-expert`、`winforms-expert` | C# 与原生 Windows 桌面专项指导 |
| 测试 | `tdd` | 重要功能先有能发现错误的测试，再实现 |
| 测试质量 | `test-gap-analysis`、`assertion-quality` | 检查漏测和“假通过”，不只报一个通过数量 |
| 排错与性能 | `diagnosing-bugs`、`analyzing-dotnet-performance` | 先复现、找原因、测量，再修复，不靠反复猜改 |
| 交付审查 | `code-review` | 分别检查代码是否符合规范、结果是否符合你的要求 |
| 安全 | `sharp-edges`、`differential-review` | 重点检查路径、覆盖、异常输入和未来真实移动的风险 |

另有 `test-analysis-extensions` 参考目录，供 AI 查 xUnit 等测试框架的规则，不是需要你调用的功能。

来源为 `mattpocock/skills`、微软官方 `dotnet/skills`、安全公司 `trailofbits/skills`；具体版本与许可见 `.opencode/skill-sources.json` 和 `docs/agents/skills.md`。

## 固定开发流程

### 1. 你说想要的效果

说清在哪个页面、现在发生什么、希望改成什么；截图可以直接标出位置。你不必给出实现方法。

可以直接这样说：

> 修改【页面/功能】。现在【现象】，希望【效果】。保留【不能改变的行为】。先给推荐方案、重要取舍和验收标准，我确认后再实现。

### 2. AI 查现状并补齐需求

AI 先检查已有实现，再用普通话说明推荐方案、修改范围、风险和验收方法。重要产品或技术取舍放进选择卡片，每项说明后果并给出推荐；不能直接让你在不理解的术语之间盲选。对于你已经明确授权、范围清楚的小修正，给出简短计划后直接执行，不制造重复审批。

界面或交互不容易说清时，先展示草图或样例。草图不是已实现功能，也不能代替真实桌面验收。

### 3. 你确认方案，再开始实现

新功能、交互调整或重要架构变化，在你确认后开始实现；没有回复不算同意。你可以接受推荐，也可以要求更简单、更安全、先做样例或暂时不做，不需要读代码证明自己的偏好合理。

需要你拍板的包括：按钮怎样工作、哪些文件允许操作、失败后保留什么，以及框架/依赖、旧数据兼容、难以撤回的架构和明显的速度/内存/维护成本取舍。AI 负责把这些技术选择翻译成具体后果，而不是代你悄悄决定。日常类名和测试写法等细节不必逐项审查，但你始终可以追问和否决。

AI 在进入需要账号、权限、工具、设备、构建签名或发布渠道的新阶段前，一次列全由谁处理、哪些已完成、哪些还缺。不能等你碰到障碍才补充条件。

### 4. AI 连贯实现并自行验证

在已确认范围内连贯完成实现、回归与适度审查，不每个文件都停下来问。遇到范围变化、方案失效、高影响操作或新的重要取舍，先停下来说明并等你确认；不能凭“技术细节由 AI 负责”扩大授权。你随时可以说“暂停”“先解释”“回到方案阶段”。

至少考虑适用的正常、错误输入、取消、失败重试、旧结果失效和旧功能不退化。文件操作另检查作用范围、已有文件保护、链接和中途失败；未来真实移动还应验证记录与恢复。使用小型隔离样本，不拿真实游戏文件试破坏性操作。

### 5. AI 交付，你看效果

每个模块交付应有：

- **改了什么**：尽量按页面和操作描述，而不是堆类名。
- **如何看效果**：可运行入口、你要点的几步、应当看到的结果。
- **验证证据**：实际执行的检查及结果，必要时提供前后截图或同条件性能数据。
- **未验证事项**：例如系统文件对话框、实际 DPI、真实桌面绘制或恢复过程；不能用编译通过冒充。

你不满意时可以说：

> 做【操作】时出现【现象】，我想看到【结果】。先核实并找根因，不要顺手改其他功能。

如果只是询问或质疑，AI 先回答和核实，不直接把它当成新的修改授权。

### 6. 你明确验收，再保存阶段成果

说“这个模块验收通过/可以了”后，AI 按项目既有规则检查改动、记录 session 编号并提交。编号没有提供时只需你补充编号；推送、发布和新增高影响操作仍需另行确认。

通过一个模块后再开始下一个模块。验收前不以“代码已写完”当成整个任务完成，也不积攒多个未经确认的大改动。

## 你不用承担的事

- 记住技能名字，或每次提醒 AI 调用。
- 为日常类名、测试接口或 Git 比较基线等实现细节逐项审批。
- 手动检查每行代码、替 AI 运行本来能自动执行的检查。
- 猜测“测试通过”到底验证了什么；AI 必须解释覆盖范围。

但任何技能都不能保证零缺陷。你看到的效果、测试证据与明确列出的验证限制，需要一起作为验收依据。

## 技能怎样主动使用

AI 按项目入口的阶段检查点主动加载匹配技能，而不是等你点名。例如：改桌面页面先用 `winforms-expert`；修故障先用 `diagnosing-bugs`；写可测试行为用 `tdd`；完整业务改动交付前用 `code-review`。不是每次把 13 个全部跑一遍。

你可以直接看到工具的技能加载记录，AI 不额外播报或汇总调用情况。回复聚焦方案、进展、效果和验证结果；你追问时再解释技能选择。写了技能名字不算实际调用，安装了也不算已经执行。

原版技能有些依赖手动触发，模型也可能漏用。本项目用 `AGENTS.md` 的显式阶段规则减少漏调，但没有安装能保证每次强制执行的程序钩子。你不用背清单，仍可随时要求解释或指定某项技能。
